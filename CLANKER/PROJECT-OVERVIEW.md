# PROJECT-OVERVIEW.md

## IDENTITY

- Name: Horus
- Type: Self-hosted uptime/monitoring platform
- Inspiration: Pingdom-style website monitoring
- Language: Go
- Primary goal: Production-oriented portfolio project demonstrating backend engineering, distributed systems, reliability, observability, and infrastructure skills.

## PURPOSE

Horus monitors external services by:

- Storing monitor configurations.
- Scheduling health checks.
- Executing HTTP checks.
- Recording check results.
- Detecting outages and recoveries.
- Creating incidents.
- Sending notifications.
- Exposing monitoring data through an API.
- Providing operational metrics and health information.

## CORE DOMAIN

### Monitor

Defines what Horus should monitor.

Core attributes:

- `ID`
- `Name`
- `URL`
- `Interval`
- `Timeout`
- `ExpectedStatus`
- `Enabled`
- `CreatedAt`
- `UpdatedAt`

### Check

Represents one execution of a monitor.

Expected data:

- Monitor reference
- Timestamp
- Status code
- Latency
- Success/failure
- Failure classification
- Error information

### Incident

Represents a continuous monitor outage.

Lifecycle:

```text
Healthy
  ↓
Check failure
  ↓
Incident opened
  ↓
Repeated failures
  ↓
Recovery
  ↓
Incident resolved
````

### Notification

Represents an outbound alert generated by an incident state change.

Potential channels:

* Email
* Webhook
* Discord
* Slack

## NON-GOALS

* Full enterprise monitoring suite
* Arbitrary browser automation
* Full synthetic browser testing
* Kubernetes-specific monitoring platform
* Complex frontend-first architecture
* Unnecessary microservice decomposition
* Feature expansion without demonstrated architectural need

## DESIGN PRINCIPLES

* Backend-first.
* Explicit domain boundaries.
* Small composable packages.
* Dependency injection where it improves testability.
* PostgreSQL as durable application state.
* Redis for asynchronous job coordination.
* Standard Go tooling where practical.
* Test behavior at package/API boundaries.
* Prefer simple designs before introducing infrastructure complexity.
* Reliability and observability are first-class concerns.
* Security is part of the implementation, not a post-processing step.

## SUCCESS CRITERIA

Horus should demonstrate:

* Clean Go architecture.
* Persistent monitoring state.
* Reliable scheduled checks.
* Concurrent worker execution.
* Incident lifecycle management.
* Asynchronous job processing.
* Notification delivery.
* Authentication and authorization.
* Production-oriented error handling.
* Metrics and observability.
* Automated testing.
* Dockerized deployment.
* Clear API and architecture documentation.
