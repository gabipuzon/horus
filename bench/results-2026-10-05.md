# Horus local load test — 2026-10-05

Host: Intel Core i5-10210U (8 logical CPUs), 7.5 GiB RAM, Linux 7.2.6,
Docker 29.8.1. All components ran on this host in Docker: Horus, PostgreSQL
17, Redis 8, and a Go mock target. The separate `horus-bench` Compose project
did not use the normal Horus database or Redis. Every monitor used a unique
`/check?id=N` URL, a 30 s interval, a 5 s timeout, and expected HTTP 200.
The target returned mostly 50–500 ms responses, with 4% at 3 s, 1% timing
out, and 2% returning 500. Each step staggered initial due times over 30 s.

Scheduling lag is `started_at - scheduled_at`, measured from persisted check
history. Throughput and lag exclude the first 30 s of each run. The queue
values below are the last sample. Rates are completed checks per second;
expected is `monitors / 30`.

At 500 monitors with 8 workers, the original checker created an HTTP
transport per check. In matched two-minute runs, Horus held 1,513 file
descriptors and used 66.88 MiB at the end before sharing a transport; after
the change it held 29 descriptors and used 12.64 MiB. Throughput was 16.58
checks/s in both runs, while p95 lag was 3.313 s before and 3.415 s after.
The 15-minute run after the change ended with 30 descriptors and 14.33 MiB,
and stored 14,492 checks in its 870 s measurement window. Its p99 lag was
3.557 s, the check table was 3,016 kB, and the database was 11 MB.

The short probes show roughly increasing throughput with more workers, but
they do not establish a linear scaling ceiling. The 15-minute result supports
500 monitors at a 30 s interval on this one host; 1,000 monitors overloaded
the same eight workers within three minutes. The precise knee between those
counts remains unmeasured. These numbers do not establish capacity on other
hardware or against external targets.

The hour-long 350-monitor soak stored 41,642 checks in its 3,570 s measurement
window. P95 lag in successive ten-minute buckets was 1.695, 1.700, 1.693,
1.700, 1.694, and 1.694 s; p99 across the run was 2.012 s. PostgreSQL mean
check-insert execution time was 0.338 ms over 42,463 calls, and the check
table was 8,800 kB in a 17 MB database at the end. Horus memory was 15.31 MiB
near minute five, 17.79 MiB near minute thirty, 17.84 MiB near minute forty,
and 16.59 MiB at the end. Final file descriptors were 30 for Horus (process
soft limit 524,287), 10 for PostgreSQL, 31 for Redis, and 15 for the mock
target.

## Replica placement probe

The main scaling series above changed `HORUS_WORKER_COUNT` in one Horus
container. A separate two-minute probe kept eight total workers and 500
monitors while distributing those workers across actual Horus containers.
Each container ran its own scheduler. The table uses the final 90 s of each
run. No duplicate `(monitor_id, scheduled_at)` pairs were observed in the
multi-container windows.

| Horus containers | Workers each | Actual / expected checks/s | p95 lag | Duplicate due checks |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 8 | 16.58 / 16.67 | 3.415 s | — |
| 2 | 4 | 16.58 / 16.67 | 3.486 s | 0 |
| 4 | 2 | 16.57 / 16.67 | 2.963 s | 0 |
| 8 | 1 | 16.60 / 16.67 | 2.897 s | 0 |

These runs show that this load was sustained with workers distributed across
multiple processes. They do not establish linear capacity scaling with more
total workers or eliminate scheduler races at other loads and start timings.
